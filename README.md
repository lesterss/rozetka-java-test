# Rozetka UI test (Selenide + JUnit 5)

Автотест для сайту [rozetka.com.ua](https://rozetka.com.ua/): збирає назви й ціни мобільних телефонів з першої сторінки каталогу та окремо — товари з лейблом «ТОП ПРОДАЖІВ».

Тести: `src/test/java/com/example/SelenideRozetkaTest.java` —

- `mobilePhonesFirstPageAndTopSales` — шлях із завдання (головна → Каталог → Телефони);
- `mobilePhonesViaDirectUrl` — запасний шлях (прямий URL каталогу), щоб перевірити збір назв/цін і ТОП ПРОДАЖІВ без меню.

## Структура коду (Page Object Model)

```
src/test/java/com/example/
  SelenideRozetkaTest.java     — декларативний тест (Given / When / Then), без $ / $$
  config/                      — BrowserSetup, прапорці -Dmanual.captcha / -Dslow.network
  model/Product.java           — назва, ціна, topSales
  pages/
    HomePage.java              — головна
    MobilePhonesPage.java      — каталог телефонів, збір товарів
    components/HeaderCatalogMenu.java — дропдаун «Каталог»
  support/
    SiteBlockHandler.java      — 500 / капча Cloudflare
    SlowNetwork.java           — CDP throttling
```

UI-дії й локатори — лише в Page Objects (`@Step` для Allure). У тесті — AssertJ для перевірок списків товарів.

## Як відкривається категорія «Телефони»

На Rozetka є кілька способів потрапити на сторінку мобільних телефонів, наприклад:

- відкрити прямий URL каталогу (`…/mobile-phones/…`);
- перейти з бокового меню головної сторінки;
- відкрити кнопку **«Каталог»** у хедері → hover на «Смартфони, ТВ і електроніка» → клік «Телефони».

У цьому проєкті є **два тести**:

1. **`mobilePhonesFirstPageAndTopSales`** — складніший шлях через дропдаун «Каталог» у хедері (ближче до завдання / поведінки користувача).
2. **`mobilePhonesViaDirectUrl`** — прямий URL `https://rozetka.com.ua/ua/mobile-phones/c80003/`, щоб швидко перевірити збір назв, цін і «ТОП ПРОДАЖІВ», коли меню або антибот заважають.

## Запуск

```powershell
# обидва тести: через меню Каталог + через прямий URL
mvn test -Dtest=SelenideRozetkaTest

# лише збір назв/цін і ТОП ПРОДАЖІВ (без меню — стабільніше для дебагу)
mvn test -Dtest=SelenideRozetkaTest#mobilePhonesViaDirectUrl

# лише шлях із завдання (головна → Каталог → Телефони)
mvn test -Dtest=SelenideRozetkaTest#mobilePhonesFirstPageAndTopSales
```

Результат (списки товарів) друкується в консоль. Якщо кирилиця в PowerShell відображається як `????`, перед запуском виконай:

```powershell
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
```

### Ізоляція між тестами

Обидва `@Test` у класі працюють в **одному** вікні Chrome за один `mvn test`. Після кожного тесту:

- очищаються cookies, localStorage і sessionStorage (`cookies().clear()` тощо; старі `clearBrowser*` у Selenide 7.17 застарілі);
- вкладка скидається на `about:blank`.

Без `about:blank` після тесту з прямим URL браузер лишався б на `/mobile-phones/`, і наступний тест візуально здавався б «одразу відкритим на мобілках», хоча далі все одно викликається `open(головна)`. Між окремими запусками Maven браузер закривається (`closeWebDriver` у `@AfterAll`).

### Повільна мережа (як у DevTools)

Щоб відтворити ситуацію «банер підвантажився пізно → дропдаун Каталогу закрився», можна сповільнити мережу в браузері тесту через Chrome DevTools Protocol (той самий механізм, що **F12 → Network → Throttling → Slow 3G**):

```powershell
mvn test -Dtest=SelenideRozetkaTest "-Dslow.network=true"
```

Можна комбінувати з ручною капчею: `"-Dmanual.captcha=true" "-Dslow.network=true"`. Після переходу на сторінку телефонів throttling вимикається автоматично, щоб збір карток не був надто довгим. Без параметра тест іде зі звичайною швидкістю інтернету.

На повільній мережі кнопка «Каталог» часто вже видима в шапці, але клік нічого не відкриває, поки Angular не довантажить обробники. Тест у такому разі клікає повторно, доки не з’явиться `rz-fat-menu` (до ~45 с при `-Dslow.network=true`).

### Ручний режим капчі

Якщо сайт показує капчу Cloudflare, тест можна запустити так, щоб її пройшла людина:

```powershell
mvn test -Dtest=SelenideRozetkaTest "-Dmanual.captcha=true"
```

Побачивши капчу, тест пише в консоль `>>> Пройди її вручну у відкритому вікні браузера` і чекає до 2 хвилин. Після проходження Cloudflare сам перезавантажує сторінку, і тест продовжує кроки. Якщо капчу не пройдено вчасно, тест падає з повідомленням `капчу Cloudflare не пройдено вручну за 2 хв`.

Без параметра (за замовчуванням) тест одразу падає з поясненням: для автоматичних запусків, наприклад у CI, людини поруч немає. Капчу тест сам не розв'язує і не обходить.

### Сторінка 500

У будь-якому режимі, побачивши сторінку 500, тест сам натискає кнопку сайту «Перезавантажити сторінку», до 2 разів. У консолі це видно як `>>> ... сторінка 500, натискаю "Перезавантажити сторінку" (спроба 1 з 2)`. Буває, що клік по кнопці сторінку не перезавантажує. Тоді через 5 с тест перезавантажує її через браузер, як F5: це та сама дія, яку мала виконати кнопка. Якщо після перезавантаження з'явилась потрібна сторінка, тест продовжує кроки; якщо знову 500 — падає з поясненням. Кількість спроб — у `SiteBlockHandler` (`SERVER_ERROR_RELOAD_ATTEMPTS`).

Коли блокування від Cloudflare вже жорстке, перезавантаження зазвичай не допомагає, і тоді лишається лише пауза або інша мережа.

## Кроки тесту

Основний тест (`mobilePhonesFirstPageAndTopSales`):

| # | Крок | Як виконується |
|---|------|----------------|
| 1 | Open rozetka.com.ua (десктопна версія) | `HomePage.openHome()` → `https://rozetka.com.ua/`, чекаємо сайдбар і «Каталог» |
| 2 | Open mobile phones page | Через меню: клік «Каталог» → hover «Смартфони, ТВ і електроніка» → клік «Телефони» |
| 3 | Get names and prices (1-ша сторінка) | Чекаємо стабільну кількість карток; з `rz-product-tile` читаємо назву (`a.tile-title`) і ціну (`.price`) |
| 4 | Get «Top Sales» | Ті самі дані, відфільтровані за бейджем `.promo-label_type_popularity` («ТОП ПРОДАЖІВ») |

Запасний тест (`mobilePhonesViaDirectUrl`) пропускає кроки 1–2 і одразу відкриває `https://rozetka.com.ua/ua/mobile-phones/c80003/`, далі ті самі кроки 3–4.

## Що перевіряє тест (валідації)

Очікування елементів (до 10 с, `Configuration.timeout`):

- на головній видима кнопка «Каталог»;
- після відкриття Каталогу видима категорія «Смартфони, ТВ і електроніка»;
- після hover у підменю з'являється клікабельний лінк «Телефони»;
- після кліку URL містить `mobile-phones`;
- сайт не показав сторінку блокування (500 або капчу Cloudflare). Перевіряється після відкриття головної і після переходу на сторінку телефонів;
- на сторінці є хоча б одна картка товару;
- кількість карток перестала змінюватись (каталог догрузився повністю, а не лише перші картки).

Перевірки результату (assertions):

- у кожного телефону **є назва**;
- список товарів «ТОП ПРОДАЖІВ» **не порожній**.

## Коли тест проходить / падає

**PASSED** — усі кроки виконались, у всіх телефонів є назва, і на сторінці є хоча б один товар «ТОП ПРОДАЖІВ».

**FAILED** — якщо хоч одна умова не виконалась:

| Причина | Як виглядає в звіті |
|---|---|
| Не відкрилось меню / не з'явилось підменю після hover | `Element not found {rz-fat-menu a[...]}` |
| Перехід не привів на сторінку телефонів | помилка `urlContaining("mobile-phones")` |
| Сайт показав сторінку 500 (`rz-server-error`), і 2 натискання «Перезавантажити сторінку» не допомогли | `Крок "...": сайт показав сторінку помилки 500 ... навіть після 2 перезавантажень` + пояснення, URL і скріншот |
| Сайт показав капчу Cloudflare (`cf-turnstile-response`) | `Крок "...": сайт показав капчу Cloudflare` + пояснення, URL і скріншот |
| Ручний режим: капчу не пройдено за 2 хв | `капчу Cloudflare не пройдено вручну за 2 хв` |
| Сторінка відкрилась, але без товарів | `Element not found {rz-product-tile[0]}` |
| Каталог довантажується довше 10 с | `Кількість карток товарів не перестала змінюватись` |
| У картки порожня назва | `У кожного телефону має бути назва` |
| На сторінці немає жодного «ТОП ПРОДАЖІВ» | `Очікували телефони з лейблом ТОП ПРОДАЖІВ` |
| Змінилась розмітка сайту (селектори) | `Element not found {...}` на відповідному кроці |

При падінні Selenide автоматично зберігає скріншот і HTML сторінки в `build/reports/tests/` — шлях друкується в повідомленні про помилку.

Товар без ціни (немає в наявності) тест не валить: у списку буде `немає ціни`.

## Звіт Allure

Після `mvn test` сирі результати лежать у `target/allure-results`. HTML-звіт (потрібен інтернет при першому запуску — качається Allure CLI):

```powershell
# відкриє звіт у браузері
mvn io.qameta.allure:allure-maven:serve

# або лише згенерувати файли → target/site/allure-maven-plugin/
mvn io.qameta.allure:allure-maven:report
```

У звіті видно: `@Epic` / `@Feature` / `@Story`, кроки `@Step`, списки телефонів як вкладення (attachments), скріншот і HTML сторінки при падінні Selenide (через `AllureSelenide`).

Списки товарів також дублюються в консоль Maven (`System.out`) — зручно під час локального запуску без відкриття звіту.

## Відповідність
Свідоме відхилення:

- у `SiteBlockHandler` лишається цикл повторів для сторінки **500** (бізнес-retry «Перезавантажити», не очікування елемента через `for` у тесті). Для Rozetka/Cloudflare це практичніше, ніж один `should`.

## Відомі обмеження

- **Hover / дропдаун Каталогу нестабільний.** Fat-menu залежить від розміру вікна (тест задає 1920x1080) і анімації. Часто на першому запуску жовтий верхній банер підвантажується пізніше і зсуває сторінку — дропдаун з'являється і одразу зникає. Тест чекає банер перед відкриттям меню і до 3 разів повторює «Каталог → hover → Телефони». Якщо меню перевіряти не обов'язково, надійніше відкрити сторінку напряму: `open("https://rozetka.com.ua/ua/mobile-phones/c80003/")`.
- **Захист від ботів.** Rozetka (Cloudflare) розпізнає автоматизований браузер за `navigator.webdriver`, чистим профілем без cookie і частими запусками з однієї IP-адреси. Тоді замість сторінки вона віддає заглушку «500 — Щось пішло не так…», а далі капчу «Трохи зачекайте…». У звичайному браузері людини цього зазвичай немає. Тест розпізнає обидві сторінки і падає з окремим поясненням, а не з «Element not found». Капчу тест навмисно не обходить. Що робити: зачекати 15–30 хвилин або запустити з іншої мережі. Ручний клік по капчі в ChromeDriver часто не допомагає — див. розділ «Ручний режим капчі».
- Перевіряється лише **десктопна версія** сайту: мобільна в завданні не вказана.
- Перевіряється лише **перша сторінка** каталогу, пагінація не використовується.
- Дані живі: кількість товарів і «ТОП ПРОДАЖІВ» змінюється від запуску до запуску, тому тест не перевіряє конкретні назви чи ціни.
